# 2026-08-24 Product Review

## 结论先行

当前 `WaterExpert Software` 已经不是“功能不够”，而是“能力太散”。它把研究原型中已经跑通的结果几乎都接进来了，但前端按产物分散展示，后端按接口分散返回，算法按脚本分散导出，最后用户看到的是一串并列页面，而不是一条完整的分析工作流。

如果用产品语言总结，这个系统现在缺的不是更多模块，而是一个主线：

1. 先把数据接进来。
2. 再把模型跑起来。
3. 接着把证据串起来。
4. 最后把结论交出去。

这件事和当前 OpenAI 的产品风格很像，核心不是“多开几个入口”，而是“把多种能力收敛到同一个任务语境里”。对 WaterExpert 来说，最该融合的不是算法本体，而是任务边界、信息架构和证据组织方式。

更重要的是，产品目标不能停在 demo。README 里“不该包装成生产级治理决策系统”描述的是当前科学边界，不是产品野心的上限。这个项目应该朝着“可持续使用、可复核、可交付、可扩展”的软件系统演进，只是它的决策输出必须始终保留 guardrails，不把经验阈值、场景 triage、playbook、Sobol、counterfactual 伪装成已经验证的治理控制策略。

参考基础主要来自：`frontend/components/waterexpert/app-sidebar.tsx`、`frontend/app/*.tsx`、`backend/app/main.py`、`backend/app/services/runtime_jobs.py`、`backend/app/services/artifact_repository.py`、`docs/architecture/software_architecture_and_interfaces.md`、`docs/handoffs/research_handoff.md`。

## 1. 当前产品问题

### 1.1 前端布局：能力罗列多，任务闭环少

现在侧边栏按“数据库、预测、边界、敏感性、知识图谱”分组，页面数量已经明显超过首版产品的认知负荷。问题不在于页多，而在于这些页之间缺少一个稳定的用户主路径。

典型表现是：

- `prediction`、`diagnosis`、`scenario`、`playbook`、`thresholds`、`boundary`、`sensitivity` 都在讲“解释”，但分别讲。
- `database`、`upload`、`preprocess`、`visualization` 都在讲“数据”，但没有串成同一次分析流程。
- `knowledge-graph` 和 `realtime` 又是另外两条线，混进主导航后会稀释核心心智。

这会让用户形成一种感觉：系统什么都有，但每次都像在换一个工具，而不是继续一个任务。

### 1.2 功能切分：同类能力被拆碎了

目前最明显的重复是“证据展示”被拆成了多个页面：

- `prediction` 展示曲线和模型对比。
- `diagnosis` 展示主导因子和过程分解。
- `scenario` 展示分诊结果和高优先日期。
- `playbook` 展示响应建议和阈值摘要。
- `thresholds` 展示经验阈值。
- `boundary` 展示边界代理识别。

这些功能本质上属于一个大能力：**解释与研判**。把它们拆成独立页面并不利于用户理解，因为用户真正想做的是“看到异常后，迅速知道它是什么、为什么、要不要管、该看什么证据”。

### 1.3 后端响应：有 job scope，但还不够像一个产品对象

后端已经有不错的骨架：`RuntimeJobService` 提供 job-scoped run directory，`ArtifactRepository` 支持按 `job_id` 切换产物，`/api/v1/*` 接口也开始支持 `job_id` 查询参数。

但从产品角度看，当前响应还像“文件读写接口集合”，不完全像“分析对象服务”：

- 有的接口天然围绕 job，有的接口默认直接读集成产物。
- 有的接口返回 summary，有的接口返回 series，有的接口返回 artifact path。
- 同一任务的状态、产物、日志、报告，还没有统一成一个稳定的对象视图。

结果就是，前端拿到的是很多块数据，但很难把它们自动编成一个“案例”。

### 1.4 数据流通：流是通的，但事件链断点太多

现在的数据链路基本可以概括为：

`导入 -> 预处理 -> 预测 -> 诊断 -> 阈值/场景/边界 -> 报告`

问题是，这条链路虽然在代码里存在，但在产品里没有被显式建模。用户看不到：

- 这次导入对应哪次任务。
- 这次任务用的是哪版配置。
- 哪些产物来自同一运行。
- 哪些证据属于同一个场景判断。

没有统一的“证据链 ID”，就很难把软件从“看结果”升级成“追踪一次分析的全过程”。

### 1.5 算法迭代：模型有版本，产品没有实验秩序

算法侧其实已经很丰富，`MSCIM`、`MSCIM-NoKG`、`CMFBE-ST-GCN`、阈值分析、Sobol、反事实、边界监督都已经在。

但产品层没有把这些能力组织成明确的迭代顺序：

- 哪个是主模型。
- 哪个是对照模型。
- 哪个是诊断增强。
- 哪个只是实验室工具。

如果没有这层秩序，功能越多，产品就越像一个研究仓库的镜像，而不是一个可持续升级的软件。

## 2. 应该怎么合并

### 2.1 前端应该从“页面集合”改成“六个主入口”

建议尽量复用现有的产品命名，不用“工作台”这种泛化词。一级导航可以收敛成下面 6 个主入口，再把轻量页收进二级页签或右侧分栏。

**A. 系统总览**
- 当前模型状态
- 关键指标
- 高优先日期
- 最近任务

**B. 数据库与数据查询**
- 数据库
- 数据导入与文件上传
- 数据预处理

**C. 浊度预测与可视化**
- 浊度与清澈度预测
- 预测结果对比
- 时序曲线与指标浏览
- 可视化分析

**D. 致浑因子诊断**
- 致浑因子诊断
- 阈值检索
- 边界变化代理识别

**E. 预计响应与问答**
- 场景分级
- 响应预案
- 实时验证
- 图谱问答

**F. 实验室**
- 知识图谱
- Sobol 敏感性分析
- 反事实分析
- 跨模态能力

这样做的好处是，用户看到的不是一串并列工具，而是从数据、预测、诊断、响应到实验室的连续路径。

### 2.2 功能应该从“并列”改成“层级”

建议把能力层级改成：

1. **发现**：预测异常、风险升高、边界变化。
2. **解释**：主导因子、过程分解、场景 triage。
3. **判断**：阈值证据、playbook、相似案例。
4. **交付**：报告导出、摘要分享、留痕。

现在的问题是，系统在第 2 层和第 3 层之间横跳，用户需要自己拼图。产品要做的是替用户拼好。

### 2.3 “实验室”不该和主业务平起平坐

知识图谱、Sobol、反事实、实时验证，这些都很重要，但它们更像支撑证据和研究增强，不适合放在主路径里占据同等权重。

更合理的做法是：

- 主路径里只展示它们的摘要。
- 详情页放在“实验室”或“更多证据”下。
- 不让用户在一开始就被研究工具分流。

### 2.4 必须从网站里删除的内容

这部分要直接告诉执行助手，避免继续沿用旧页面的说法。

- 删除 `系统总览` 页里的 `推荐智能体查询` 模块，不再展示推荐问题列表。
- 删除所有面向用户的“单站多模态、日尺度原型、仅有吴淞口站点”之类描述，不要把产品页面写成研究介绍。
- 删除前端可见的“事实边界”与“免责声明”模块；如需保留约束，只放在内部文档、接口说明或后端日志，不进入网站主界面。
- 删除独立的 `数据预处理` 页面；预处理功能可以保留在后端和任务流里，但不再作为一个单独入口。
- 删除一切只承载目录跳转、且页面主体不足一屏的入口页，统一并入父页面的页签、折叠区或右侧证据栏。

## 3. 后端应该怎么改

### 3.1 统一对象模型

后端建议明确四个核心对象：

- `Import`：一次导入。
- `Job`：一次分析任务。
- `Case`：一次可解释分析案例。
- `Report`：一次交付结果。

现在这些对象有的已经存在，有的隐含存在，但没有统一命名。建议把 `dashboard`、`predictions`、`diagnostics`、`scenario-triage`、`thresholds`、`boundary`、`sensitivity` 都尽量挂到 `job_id` 或 `case_id` 上。

### 3.2 统一响应信封

建议所有核心分析接口都补齐这些字段：

- `artifact_scope`
- `job_id`
- `generated_at`
- `source_artifacts`
- `guardrails`

这样前端才能判断这份数据来自集成产物、任务产物，还是实验室产物。

### 3.3 让状态机更像产品

`RuntimeJobService` 现在已经比早期版本成熟很多，但建议继续往“可解释状态”收敛：

- `queued`
- `running`
- `completed`
- `failed`
- `orphaned`

同时，把日志、状态文件、产物清单都纳入同一个 job 视图。否则用户只看到“任务完成了”，却不知道它完成在哪、用了什么、产出了什么。

## 4. 数据流应该怎么通

### 4.1 把分析流程显式化

建议把系统主流程写成一条固定管线：

`导入 -> 清洗 -> 对齐 -> 建模 -> 解释 -> 证据汇总 -> 报告`

每一步都要留下可以被前端读取的结构化结果，不只是 CSV/JSON 文件本身。

### 4.2 把“同一次分析”的证据打包

一份分析案例最好包含：

- 输入数据摘要
- 配置快照
- 模型版本
- 预测结果
- 主导因子
- 场景标签
- 阈值证据
- 边界证据
- 报告链接

这会比单独打开六个页面更像一个专业产品。

### 4.3 把实验产物和产品产物分层

现在仓库里既有核心产品输出，也有研究实验输出。建议明确分层：

- 产品层默认展示 `outputs/metrics`、`outputs/agent`、`outputs/diagnosis`、`outputs/thresholds`、`outputs/boundary`。
- 实验层放 `outputs/sensitivity`、`outputs/counterfactual`、`knowledge-graph`、`cross-modal`。

这样不会把“可交付结果”和“研究增强结果”搅在一起。

## 5. 算法迭代应该怎么排

### 5.1 主模型只保留一个默认叙事

产品默认叙事应该是：

`MSCIM` 是主预测与诊断模型，`MSCIM-NoKG` 是对照，`CMFBE-ST-GCN` 是机制增强解释层。

不要在首页同时把三者当成三条平行主线，否则用户不知道应该信谁。

### 5.2 把模型迭代做成可比较的实验台

建议增加一个固定的“模型实验台”：

- 模型版本比较
- 指标对比
- 解释差异
- 阈值差异
- boundary head 差异

这部分应该面向研究人员，而不是普通业务用户。

### 5.3 让算法输出服务于“案例复盘”

模型每次更新，都要能回答三件事：

1. 预测有没有更准。
2. 解释有没有更稳。
3. 报告有没有更好读。

这比单纯追求更多指标更符合软件产品节奏。

## 6. 改造期望

我认为这类项目的合理目标不是“把研究结果做成一个能看图的 demo”，而是把它推进成一套真正可持续交付的软件产品。

这个期望至少包括四层：

1. **可用**：研究人员和业务分析人员能稳定完成导入、分析、诊断和导出。
2. **可复核**：每个结论都能追溯到输入、配置、模型版本和产物。
3. **可扩展**：后续可以继续接多站点、多模型、多任务，而不是每加一个能力就重做一页。
4. **可运营**：任务、日志、状态、报告和权限逐步形成软件系统，而不只是脚本集合。

这里的“可运营”不是指把当前原型直接说成生产级治理系统，而是指它要具备上线前的软件骨架，能长期维护、持续迭代、逐步加固。换句话说，不能满足于演示级漂亮页面，而要把每一个页面都变成真实工作流的一部分。

## 7. 建议的导航结构

我建议下一版直接按下面的结构重组：

- `总览`
- `数据库与数据查询`
- `浊度预测与可视化`
- `致浑因子诊断`
- `预计响应与问答`
- `实验室`

其中：

- `database`、`upload` 合并到“数据库与数据查询”；`preprocess` 不保留独立页面。
- `prediction`、`visualization`、`realtime` 合并到“浊度预测与可视化”。
- `diagnosis`、`thresholds`、`boundary` 合并到“致浑因子诊断”。
- `scenario`、`playbook`、`knowledge-graph/qa` 合并到“预计响应与问答”。
- `knowledge-graph` 的构图、`sensitivity`、`counterfactual`、`cross-modal` 作为“实验室”。

从内容密度看，`thresholds`、`boundary`、`realtime` 这类页面都属于单卡片或单表结构，单独占一级导航会显得碎，适合并成上一级页面里的页签、折叠区或右侧证据栏。

`knowledge-graph` 的总览页更像目录页，也适合并入“实验室”作为入口面板，而不是继续单列成主业务入口。

## 8. 优先级建议

### P0
- 统一导航和页面分组。
- 把预测、诊断、场景、阈值、边界收进统一的分析入口。
- 把 `thresholds`、`boundary`、`realtime` 这类单屏页并入主入口的页签或证据栏。
- 给核心接口补齐 `job_id` / `artifact_scope` / `generated_at` 语义。

### P1
- 建立 case 级证据包。
- 报告页支持“从任务生成报告”与“从案例生成报告”两种入口。
- 主动轮询任务状态，减少手动刷新。

### P2
- 实验室与主业务分流。
- 知识图谱、Sobol、反事实、实时验证做成研究增强区。
- 建立模型版本对比和发布节奏。

## 9. 一句话判断

这个项目的下一阶段，不该再往“更多功能”走，而该往“更少入口、更强串联、更清晰证据链”走。

只要把能力合并成工作流，WaterExpert 就会从“研究结果集合”变成“可交付的软件产品”。
